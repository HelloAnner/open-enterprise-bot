企业级 Bot 技术架构

一、目标与范围

对外是可持续收发消息的 Bot 对话，对内是异步推进的任务与后台执行。每位用户由一个独立 Router 统一协调，同一用户的多个 Bot 共用该实例。长任务交给 Ticket 和 Worker，由 Job 在后台实际执行；用户不必等任务结束才能继续发送消息、切换 Bot 或发出控制指令。

本稿固定后端的概念、归属、事件流和安全边界。每位用户拥有一个 microVM；多个具有独立身份的 Bot 在其中共享运行环境，同时保留各自的会话、长期记忆与屏幕。Router Pool 管理用户级 Router 实例，不在不同用户间共享提示词或会话状态。

这里的 ReAct 指 Agent 的推理与行动循环，不是前端 React 框架。“异步 ReAct”意味着推理、消息收发、控制与后台执行解耦，而不是把整个循环包装成一次必须等待完成的调用。

Grok bot 与 DeepSeek Super Agent 仅作为设计理念的讨论参照，本阶段不合并两者的完整机制。当前聚焦分层、事件订阅、异步执行和隔离边界，不引入额外的自治层级。

当前为概念设计，不代表已有实现。Event Bus 等名称表达逻辑职责；数据库、消息中间件、通信协议、模型框架、microVM 产品和部署拓扑均未选型。下文标识、事件名及目录均为示意。

三、核心概念与会话分层

概念职责与归属必须区分的边界
Bot用户拥有的独立身份，具有独立会话、长期记忆与屏幕。同一用户的多个 Bot 共用一个 microVM 和一个用户 Router，但不合并 Bot 身份。
Trigger / Channel GatewayTrigger 表示触发入口；Gateway 适配渠道输入、输出并将输入序列化为 Events。接入适配不承载 Agent 推理；事件序列化不等于让所有任务串行执行。
Event Bus异步传递用户输入、模型输出、控制及后台执行事件。事件传递与模型调用解耦；不是每种事件都需要一次 Router 推理。
Policy对事件来源、发起者、目标用户 / Bot 和可用权限进行授权过滤。是否允许处理、是否需要回复、允许执行什么，是不同判断；订阅和 Job 控制也受约束。
Router Dispatch消息中转职责：校验路由范围，结合 Thread 与订阅，将事件送到对应接收方。是确定性分派，不是一个供所有用户共享提示词的 Router Agent。
Router Pool管理按用户隔离的 Router 实例集合。一个用户对应一个逻辑 Router；Pool 不是随机借出一个没有用户归属的会话。
Router用户范围内的 Super Harness / Main Session，统筹该用户的多个 Bot、任务与对人沟通。不同用户有独立实例与提示词；同一用户的 Bot 不各自创建 Router。
Thread连续事件的归并载体，保留同一过程中的事件序列。不是单个 Ticket 或模型 Session；与 Ticket 通过多对多订阅关联。
Ticket一个具体子任务的执行单元，拥有独立 Work Session、上下文和工作目录。由用户 Router 创建，可订阅多个 Thread；负责任务，不直接占住整段用户对话。
WorkerTicket 下属的执行协调者，可承载 Sub Agent，拥有独立 Session 与目录。通过异步操作管理 Job，感知进度和变更；不把后台 Job 当成一次阻塞工具调用。
JobWorker 下属、实际在后台执行具体操作的运行单元。有独立 job_id 和运行状态，不是新的 Bot、Ticket 或 Agent Session。
Artifact执行形成的可交付产物，例如报告、文件或结构化结果。归属 Ticket，关联 Worker / Job 来源；不等于进度消息或执行日志。
三层会话，一层后台执行：用户 Router 的 Main Session 负责协调对话；Ticket 的 Work Session 负责一个任务；Worker Session 负责具体步骤与 Job 控制；Job 负责实际运行。Ticket 使用任务根目录，Worker 使用独立子目录；Job 不因此新增一层模型会话。

本稿将“唯一 Router”的范围明确为用户，而非整个系统。用户级协调状态与 Bot 会话 / 长期记忆分开管理；复用 Router 实例不等于混用 Bot 上下文，也不要求每用户独占一个操作系统进程。

四、单用户 microVM 与多 Bot 共享边界

Bot 独立逻辑状态 同一用户内共享的运行能力 用户级 microVM 边界

屏幕独立是交互视图的独立，不是浏览器账户或凭据的隔离。共享浏览器上的登录态变更、窗口操作与 Job 资源竞争需要协调。microVM 与 Router 都有用户归属，但不预设 Router 必须部署在该 microVM 内；屏幕映射与运行时部署方式尚未确定。

不要把逻辑隔离写成安全沙箱。不同目录和 Session 可以区分任务状态，但不能独自阻止同一 VM 内的不可信代码越权。若开放任意代码执行，仍需明确进程权限、工具授权和资源访问限制。

五、Thread 与 Ticket 的事件路由

Thread 记录连续发生了什么，Ticket 负责推进某一件事。两者通过订阅建立多对多关系：一个 Thread 可被多个 Ticket 订阅，一个 Ticket 也可同时关注多个 Thread。订阅表达事件兴趣，不赋予额外权限。

Thread 事件流 授权后的订阅投递 任务执行与对话统筹

订阅投递由 Event Bus 与 Router Dispatch 承载，直接唤醒 Ticket，不要求用户 Router 每次都运行一轮模型推理。首次事件尚无订阅，先交该用户的 Router；图中只展开后续事件的订阅路径。

事件情形谁处理对外行为
首次触发 / 没有匹配订阅中转层经 Policy 放行后，交 Router Pool 中对应用户的实例；需要长任务时创建 Ticket，并由 Ticket 建立订阅。用户 Router 决定是否回复，通过目标 Bot / 会话返回。
后续事件 / 已有匹配订阅中转层按订阅直接交给相关 Ticket，推进既有任务；不要求用户 Router 逐条重新分派。Ticket 汇报状态与结果，Router 按需整理，不必逐事件打扰用户。
人的新消息 / 即使已有订阅仍交用户 Router 理解意图；相关 Ticket 可同时消费获准事件，再将变更送达 Worker，而不等待当前 Job 完成。共享同一 Router，但按 Bot 身份和来源会话分别回应。
Job 进度 / 完成 / 失败 / 停止Job 事件按所属关系送达 Worker，经 Ticket 汇总；需要决策、授权或交付时再交用户 Router。后台执行不直接向人发言，也不把每条日志都转成一次 Router 推理。
旁路的是重复编排，不是人机对话。同一事件可能既需要 Router 判断人的意图，也需要已有 Ticket 继续工作；Router 不应仅因再次收到事件就重复创建相同任务。

六、Router Pool 与用户级统筹

每位用户一个独立 Router，同一用户的多个 Bot 共用该实例。不同用户可以有不同提示词、配置与 Main Session 状态；用户在 Bot A 等回复时，可以继续与 Bot B 交互，而不是为每个 Bot 分配一个互不协作的 Router。

Bot 入口集合 / 实例池 确定性消息分派 独立用户 Router / 定向投递

规模数字只说明实例归属，不是容量测试或部署承诺。用户级逻辑实例不等于独占进程、线程或模型连接；激活、回收与横向扩容方式留待实现设计。

  • 用户间隔离：用户 U1 的提示词、协调状态和任务集合不进入用户 U2 的 Router。
  • 用户内复用：同一用户的多个 Bot 共享 Router 的协调能力，但每次处理仍携带 Bot 身份、来源渠道与会话引用，按授权装载会话及记忆。
  • 并发而不串话：Bot A 的模型输出或长任务不占住 Bot B 的输入通道；回复仍返回对应 Bot / 会话，不因共享实例而自动跨 Bot 广播。

七、异步 ReAct 与全双工通信

输入、输出、控制与后台执行可以同时发生。系统不采用“用户发一条消息，等待整轮模型与工具全部完成，才能处理下一条”的阻塞模式。模型生成过程中可以接收新消息；Job 在后台运行时，Worker 仍可接收进度、取消或更新事件。

事件类别示意事件投递与处理
用户输入user.messageGateway 规范化后进入 Event Bus，经授权中转送到用户 Router；匹配订阅时也可唤醒既有 Ticket。
模型输出model.delta / model.message按输出目标返回对应 Bot / 会话，不要求用户停止输入，也不作为新的用户请求再次触发 Router。
控制指令control.update / control.cancel携带明确作用目标，送达相关 Ticket / Worker；取消模型生成与停止某个 Job 是不同作用范围。
后台执行job.progress / job.completed / job.failed / job.stopped送达所属 Worker，恢复其后续判断；通过 Ticket 向用户 Router 汇总，而不是直接面向用户发言。
序列化事件，不是串行等待任务。Gateway 将渠道消息转换为统一事件结构；必要的会话状态更新可以短暂顺序化，但不能用一个覆盖整段模型生成或 Job 生命周期的锁，阻塞同一用户所有 Bot 的收发与控制。

这里的全双工是系统级收发与控制语义，不要求飞书、企业微信等渠道使用同一条双向 Socket；Gateway 适配各渠道的接收与发送能力，具体协议未选型。异步也不意味着模型没有生成延迟。

对话 / 任务协调 / 定向控制 Job 操作与后台事件 虚线表示确认、回传或结果；竖虚线为生命线

为突出并发关系，图中省略 Gateway、Event Bus 与 Router Dispatch，消息仍通过第二节的传递链路。J1 运行期间的对话无需等它结束；⑭—⑰ 只表示需要替换执行的分支，单纯停止时不启动 J2。

  • 收发解耦：模型输出尚未结束，也必须能够接收人的新消息和控制事件；后台 Job 不占住 Router 的长回合。
  • 事件触发续行：Worker 提交 Job 后保留关联状态，将后续判断交给进度、完成、失败或控制事件触发；不需要持续阻塞等待，也不依赖高频 Status 轮询维持对话。
  • 控制有目标：自然语言变更由用户 Router 理解，目标明确的控制送达所属 Ticket / Worker。不能因为同一用户在 Bot B 说话，就自动停止 Bot A 的全部 Job。
  • 区分输入与输出：事件类型、来源与目标必须明确；model.delta 和 job.progress 的传递，不等于重新发起用户请求，避免输出回流形成推理循环。
  • 合并不丢关键状态：常规进度可以批量整理，但取消、失败和最终完成事件不能仅作为进度噪声被忽略；具体调度优先级与背压策略尚未定义。

八、Worker、后台 Job 与统一交付

Worker 做判断，Job 做实际执行

  • Ticket 持有任务目标、工作上下文与独立工作根目录；Worker 持有独立 Session 和工作子目录，可承载 Sub Agent。
  • Worker 根据任务和事件决定 Start、查询 Status、Stop，或调整参数后重新执行；Job 在后台完成具体操作，不承担对人沟通。
  • 一个 Worker 可管理一个或多个 Job，每个 Job 归属明确的 Worker。Job 完成或用户变更到达时，Worker 都能收到相应事件并重新判断。
  • Worker 只汇报已受理、运行中、已停止或已完成等真实状态，不把“发出命令”当成“执行成功”。

目录示意：/bots/{bot_id}/tickets/{ticket_id}/workers/{worker_id}/。Job 的进程、运行位置和输出目录细节尚未选型。

逐级汇总，由用户 Router 对外交付

  • Job 进度和完成事件返回所属 Worker；Worker 通过 Ticket 汇报任务级进度、阻塞和 Artifact，不直接向任意渠道发消息。
  • 用户 Router 将多个任务的信息整理后，通过 Channel Gateway 以正确 Bot 身份返回指定会话。
  • Bot 长期记忆、Main Session 协调状态、Ticket 工作上下文、Worker 临时上下文与 Job 运行状态分别管理，不默认把执行日志写入长期记忆。
  • 不同 Worker 不默认共享对话历史和临时文件；协作使用明确输入、结果引用或 Artifact，权限不得高于所属 Ticket。
概念操作统一记为 Start / Status / Stop；操作名说明职责，不是已冻结的 API。
操作即时结果后续如何推进
Start提交执行请求，返回受理状态与 job_id；不等待实际工作完成。Job 在后台运行，以进度、完成或失败事件通知 Worker；启动失败也必须有明确结果。
Status查询指定 Job 的当前状态快照，不等待它达到完成状态。用于主动查询、状态核对或恢复后的对账；正常续行主要由事件触发，而非忙等轮询。
Stop请求停止指定 Job；已受理不等于已经停止。等待停止确认或核对实际终态。若完成与停止并发，以真实状态为准；不能承诺撤销已产生的外部副作用。
更新任务不等于重用旧结果。当前用“Stop 旧 Job，再按新参数 Start 新 Job”表达需要重新执行的变更，不额外引入热修改接口。新一次执行具有新的 job_id；旧 Job 的迟到事件保留来源，但不能覆盖新执行的状态或产物。

取消与完成存在竞态。Worker 必须跟踪当前执行关联，确认旧 Job 的实际状态；争用同一浏览器、文件或其他资源时，不能在尚未停止旧操作的情况下假定资源已安全释放。强制终止、补偿与重试策略留待后续定义。

九、凭据、敏感输入与授权

Vault · 密码箱

凭据由受控的密码箱保存。Router、Ticket 与 Worker 使用凭据引用和授权范围表达需求，不把明文密码或令牌放入模型上下文。

实际凭据只在已授权的工具 / Job 执行边界使用。共享浏览器或同一个用户 Router，不意味着所有 Bot、Ticket、Sub Agent 和 Job 自动继承全部凭据使用权。

Security Form · 安全表单

需要敏感信息或授权确认时，通过安全表单完成，而不是要求用户在普通聊天中发送密码。提交结果关联相应 Ticket，以事件恢复后续任务。

Router 只需获得“待提交 / 已提交 / 已授权”等状态；等待表单的任务不阻塞其他对话。Ticket 获得获准使用的引用或结果，表单提交不是绕过 Policy 的第二条入口。

  • 入口与路由：Gateway 校验来源，中转层按经过验证的用户 / Bot 身份进行 Policy 过滤和实例选择；不能直接信任外部载荷中的 user_id 或执行目标。
  • 执行与控制：订阅投递、工具调用、Job 的 Start / Status / Stop 和 Artifact 访问都要校验当前权限；持有 job_id 或其他对象标识本身不是授权。
  • 敏感数据：密码、令牌和安全表单原始敏感输入不进入普通对话、长期记忆、执行日志、Event Bus 的普通事件载荷或 Artifact。
  • 审计关联：保留事件、授权决策、用户 Router、Ticket、Worker、Job 和 Artifact 的关联记录，但不记录敏感输入明文；取消和重启也保留操作来源。

本节定义必须保留的安全边界，不预设密码箱产品、加密密钥体系或表单实现方式。

十、逻辑数据关系与后续边界

逻辑字段示意：用于区分身份、事件目标与执行归属，不代表已冻结数据库表结构或 API。
逻辑记录必要标识 / 引用示意关系约束
Botbot_id、user_id、身份 / 记忆 / 屏幕引用归属用户；用户内共用 microVM 与 Router，但 Bot 会话和长期记忆分别管理。
Routerrouter_id、user_id、提示词 / 配置 / 协调状态引用每用户一个逻辑实例，由 Router Pool 管理；不同用户的提示词和状态隔离。
Main Sessionmain_session_id、router_id、Bot / 对话上下文引用归属用户 Router；按 Bot 与会话装载上下文，保留各 Bot 的独立身份和回复目标。
Eventevent_id、user_id、类型、来源、目标、关联与载荷引用区分输入、输出、控制和后台事件；按类型关联 Bot、Thread、Ticket、Worker 或 Job。
Threadthread_id、用户归属、来源会话 / 连续过程引用承载多个连续事件，不等于模型调用、Ticket 或 Job。
Subscriptionthread_id、ticket_id、订阅范围与有效状态Thread 与 Ticket 多对多；中转层匹配投递时仍校验用户归属与当前授权。
Ticketticket_id、router_id、bot_id、Work Session / 目录引用由用户 Router 创建，保留任务来源 Bot；独立承载任务上下文，可派生多个 Worker。
Workerworker_id、ticket_id、Session / 目录 / 当前执行关联归属一个 Ticket，可管理多个 Job；通过事件推进判断和控制，不等同于后台进程本身。
Jobjob_id、worker_id、运行状态、输入 / 输出 / 控制关联归属一个 Worker；重新执行产生新标识，迟到事件不能覆盖新的当前执行。
Artifactartifact_id、ticket_id、Worker / Job 来源、存储 / 访问控制引用可追溯到任务与具体执行；由用户 Router 统一呈现，访问权限仍需单独校验。

事件中的身份必须来自可信接入或内部运行时，相关对象必须校验归属与授权；并非所有事件都有 thread_id 或 job_id。跨渠道 Thread 归并、事件顺序与投递保证尚未确定，不能把事件“并发可达”写成“全局天然有序”。

本轮固定的架构约束

  • 一个用户一个 microVM、一个逻辑 Router；同一用户的多个 Bot 共用两者，Bot 身份、会话、记忆与屏幕仍独立。
  • Gateway 将渠道输入规范化为 Events，经 Event Bus 和 Router Dispatch 到达目标用户 Router；Policy 在执行与投递前生效。
  • Router Pool 按用户隔离提示词和状态；不存在一个供所有用户共享上下文的 Router。
  • 输入、模型输出、控制与后台事件可并行；不等待整轮 ReAct 或后台 Job 结束才接收新消息。
  • Thread 与 Ticket 多对多订阅；已有订阅可直达任务，对人沟通仍由用户 Router 统一统筹。
  • Ticket 与 Worker 独立会话及目录；Worker 通过 Start / Status / Stop 管理 Job，最终产物称为 Artifact。

后续逐项设计，不在本轮预设
