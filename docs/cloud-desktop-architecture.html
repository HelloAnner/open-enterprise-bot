用户级云电脑：选型与技术架构

一、选型结论与资源基线

选择 Firecracker microVM 作为每位用户的云电脑底座。同一用户的多个 Bot 共用一台电脑、浏览器环境与持久磁盘，但拥有各自的屏幕视图。业务应用 Pod 只是控制入口，不是云电脑或用户数据的所有者；应用重启不能连带删除、重建或清空用户电脑。

1 microVM每位用户一个逻辑云电脑
2 vCPU每台 VM 的虚拟 CPU
4 GBGuest 内存，不含宿主开销
40 GB每用户持久磁盘初始容量

云电脑内提供 Chrome、文件系统与文件浏览器、Shell / 终端、Python 环境、常用字体，以及可被 VNC 访问的软件渲染桌面。Compute Manager 提交生命周期操作，Desktop Gateway 负责鉴权与分发，独立的 Compute Agent 管理 Guest 内的桌面和执行能力。

这是最低起步规格，不是十个 Bot 满载并行的性能承诺。2 vCPU 不代表两颗独占物理核心。内存 API 建议统一按 4096 MiB（4 GiB）配置；磁盘 40 GB 按十进制容量表达，包含系统、软件与用户文件，实际可用空间低于标称容量。最终容量和计费单位在实现前统一。

本专题将总架构中待定的 microVM 底座明确为 Firecracker；分层背景见 企业级 Bot 技术架构。本文是设计文档，不代表 VM、桌面镜像或控制服务已经实现；具体 Firecracker、Guest 内核及软件版本尚未锁定。

二、调研依据与能力边界

依据公开资料能确认什么本方案如何使用
Grok Bot官方文档说明：用户拥有持久的 Firecracker microVM；同一用户的 Bot 共享电脑、文件与浏览器会话，每个 Bot 有自己的屏幕。[1]借鉴用户级计算隔离与 Bot 级工作视图；不推定其内部 Gateway、屏幕服务或控制 API 的具体实现。
Firecracker提供基于 Linux / KVM 的精简虚拟化与块设备、网络、vsock 等能力；官方列出的基础设备模型不含常规显卡 / 图形桌面。[2]采用它隔离 Guest，而不是把它当成开箱即用的 VDI。虚拟显示、VNC、字体、浏览器和桌面管理由 Guest 镜像补齐。
持久块存储Firecracker 的 virtio-blk 由宿主文件或块设备支撑；磁盘是否持久取决于这些后端资源及写入策略。内存快照与磁盘管理不是一回事。[3][4]用户盘独立于应用 Pod 和 VM 进程保存；明确刷盘、挂载、备份、删除与故障恢复规则。

Compute Manager、Desktop Gateway、Compute Agent 的分工，以及后文的屏幕分区方案，是本项目的架构设计，不是对 Grok Bot 内部实现的复述。

三、分层架构与组件职责

应用控制 / 用户 Guest 独立网关、运行与持久化能力 应用 Pod / 计算节点边界

VM Runtime 是必要的宿主侧执行职责，不是新增的业务 Agent。Guest 内的 Compute Agent 无法给已关闭的自身 VM 开机；真正的开机、进程终止、磁盘挂载必须由宿主运行时执行。

组件部署与职责不应承担什么
Compute Manager位于业务应用 Pod 内；校验操作权限，记录期望状态，提交开关机请求，向 Router 回报操作状态。不在 Pod 内启动长期存活的 Firecracker 子进程；不把用户盘放进容器文件系统或 emptyDir。
Desktop Gateway独立部署；把控制、Agent RPC 与屏幕会话定向到正确 desktop_id、节点和 screen_id；处理鉴权与重连。不把自身内存里的路由表当唯一事实，不将 VNC 转发当作数据持久化。
VM Runtime在具备 Linux / KVM 的独立计算节点上运行；管理 Firecracker / jailer、网络、卷挂载和节点级资源。不受业务 Pod 的进程树、cgroup 或发布清理规则连带终止；管理接口不直接暴露给浏览器或 Guest。
Compute Agent建议每用户 VM 内一个独立 Agent；管理桌面服务、屏幕映射、浏览器、文件 / Shell / Python 入口与 Job 控制关联。不替代用户 Router 的对话与业务规划；不把“独立 Agent”误解为每个 Bot 再分配一台 VM。
Registry / 用户盘持久保存云电脑归属、运行绑定、屏幕规格和数据卷；生命周期独立于应用与网关进程。不因 Pod 重启、控制连接断开或普通关机自动删除。

四、Guest 软件栈与 Compute Agent

能力首版建议组件设计说明
系统与服务管理精简 Linux Guest、init / 服务监督、非 root 工作用户优先统一 x86_64 的宿主 / Guest 镜像组合，便于验证浏览器与系统依赖；具体发行版和内核版本需锁定。
软件渲染桌面Xvfb + Openbox 等轻量窗口管理器在 Guest 内创建软件虚拟显示；不依赖 Firecracker 提供显卡，不将 GPU / 3D 加速写成已有能力。
远程屏幕Guest 内 x11vnc；Web 端复用 noVNC，网关侧适配 WebSocket / RFBVNC 只通过受控隧道访问，不把 Guest 的 VNC 端口直接暴露公网；复用成熟协议组件，不自造远程桌面协议。
浏览器Chrome；用户级持久 Profile；受控浏览器操作入口Profile 和登录态归属用户盘；镜像固定发行版与版本，保留浏览器沙箱，不用关闭安全机制换取“能启动”。
文件与文档预览Thunar 等轻量文件浏览器；Chrome 的 PDF / 图片能力工作文件、下载与 Artifact 输出进入持久目录；额外办公软件按明确文件格式需求再加入，不预装整套重型软件。
Shell 与终端Bash、coreutils、轻量图形终端命令可在后台 Job 执行，桌面终端用于查看或接管；命令权限、目录归属与资源限制单独控制。
PythonPython 3、venv、pip 与按需安装的库任务环境和需要保留的依赖落盘；对安装来源、磁盘占用与进程资源做约束，不把任意 pip 安装视为无风险。
常用字体Noto CJK、DejaVu / Liberation、按需 Emoji 字体覆盖中英文、常见符号和文档渲染；专有字体需要授权，不能假定系统自动具备所有 Office 字体。
Compute Agent独立身份与权限的桌面管理 Agent；由 Guest 服务管理器监督暴露观察 / 控制 / 文件 / 命令能力，维护 screen_id 和 Job 关联；具体动作通过受控工具执行，不让模型直接调用宿主管理 API。
microVM 启动完成，不等于云桌面已可用。Ready 至少需要 Guest Agent 可达、用户盘挂载正确、虚拟显示可获取画面、浏览器与工具依赖通过检查；不能把 Hypervisor 的启动时间当成用户看到桌面的耗时。

这些是建议镜像组件，不是已经构建好的镜像。CPU 软件渲染、WebGL、视频、中文字体和文件预览必须在 2 vCPU / 4GB 基线上实际验证。

五、同一 VM 内的独立屏幕与共享浏览器

独立屏幕指 Bot 的工作视图，不指独立 VM、独立显卡或独立浏览器账户。同一用户的十个 Bot 可以各自拥有 screen_id，但仍共享浏览器 Profile、文件与计算资源。不能为实现多屏而悄悄改成十份互不共享登录态的浏览器环境。

Bot 独立工作视图 用户共享资源 / 画面与输入传递 同一用户计算边界

Chromium 文档明确：两个运行中的独立 Chrome 实例不能共享同一个 user data directory。x11vnc 上游文档支持用 -clip 将一个显示空间分区导出到不同查看器。两项事实支持此方案的组件选择，但不能代替完整多屏 PoC。[5][6]

  • 屏幕标识稳定，连接可重建：持久保存 Bot 与逻辑 screen_id 的关系；DISPLAY、窗口 ID、VNC 会话与连接地址是运行时绑定，VM 冷启动后可以重新分配。
  • 观察可以并行，GUI 输入需要仲裁：共享 X 会话有全局焦点。自动操作与人工接管必须持有短期控制权，正确设置目标窗口，执行后核对画面；不能让多个 Bot 交错输入到错误窗口。
  • 弹窗与新窗口必须验证：窗口管理器需处理弹窗、系统对话框、全屏、文件选择器和窗口越界。单纯截图裁剪并不能保证输入始终落在正确屏幕。
  • 共享登录态具有真实影响：一个 Bot 退出账户、改变 Cookie、修改或删除文件，会影响同用户的其他 Bot；订阅或任务并发不能消除这些资源冲突。
屏幕不是 Bot 间的安全边界。同一 Guest 中的任意 Shell / 代码可能访问共享文件、浏览器 Profile 与显示会话。当前按用户划分计算安全域，不能声称仅靠目录、窗口或 screen_id 就实现了恶意 Bot 之间的强隔离。

六、用户盘、控制目录与持久化规则

电脑身份、持久磁盘、运行中的 VM 进程，是三个不同对象。建议首版为每位用户分配一块 40GB 的可写持久根卷，包含 Guest 系统、桌面软件、用户文件、浏览器 Profile 与需要保留的 Python 环境。首次从版本化基础镜像初始化，之后开机继续使用同一 volume_id，不在每次 Start 时重新复制模板。

数据 / 状态保存位置与要求恢复时如何处理
用户与云电脑归属独立持久目录：user_id、desktop_id、资源规格、volume_id、镜像版本与期望状态。新 Manager / Gateway 读取原记录，不因原 Pod 消失而生成第二台逻辑电脑。
运行绑定与操作记录保存当前节点、VM 代次、Agent 端点、操作 ID 与结果；缓存可丢，事实记录不可仅在进程内存。先查询实际运行状态再重建连接；用代次与单写入者约束防止旧实例继续使用同一用户盘。
文件、浏览器与软件环境40GB 用户持久卷；底层采用可跨计算节点重新挂载的持久块存储，不只放在计算节点的临时本地盘。同一卷重新挂载后保留已可靠落盘的数据；网站登录是否仍有效由网站会话策略决定。
Bot 屏幕规格逻辑 screen_id、Bot 归属、分辨率与视图映射规格进入持久目录。恢复屏幕布局并重新创建连接；不承诺所有临时窗口或内存中未保存的表单原样还在。
运行内存与临时画面RAM、焦点、未落盘缓存与普通 VNC 连接不是磁盘数据；不默认持久化。业务 Pod 重启时可继续存在于独立 VM；Guest / 宿主重启时通常丢失，需冷启动或经过验证的快照恢复。
首版以“可靠磁盘 + 冷启动恢复”为基线。关机保留用户盘；删除云电脑是单独的授权操作。Firecracker 使用宿主文件 / 块设备承载磁盘，不把它描述成自动管理远程存储、备份或原生 qcow2 增量克隆的平台。

不能省略的写入与挂载约束

  • 持久卷路径交给 Firecracker virtio-blk，建议采用支持 Guest flush 的 cache_type=Writeback，并验证文件系统 fsync、宿主与存储链路的耐久语义。
  • 官方文档中的默认 Unsafe 不提供相同的 flush 语义，不能只因“写进了磁盘文件”就宣称断电也不会丢失。[3]
  • 同一用户卷只允许一个活动写入者。节点失联时先隔离旧实例 / 解除旧挂载，再让新节点接管，不能通过同时启动两台 VM 试探恢复。
  • 若通过 Kubernetes PV / PVC 接入存储，应配置适合用户数据的保留策略并与业务部署解绑；PV 的持久性与回收策略仍须显式管理。[7]

快照与备份不是同一件事

  • Firecracker 快照包含 Guest 内存 / VM 状态；磁盘后端仍需另外管理，并与内存状态取得一致恢复点。[4]
  • 磁盘备份用于数据恢复，内存快照用于可选的快速恢复；一个不能自动替代另一个，也不能默认拿快照实现任意跨主机迁移。
  • 快照恢复受 CPU 特征、Firecracker / 内核兼容性和外部资源约束；启用前必须验证目标宿主组合。[4]
  • 备份与内存快照可能含 Cookie、令牌或敏感页面，必须加密、限制访问、规定保留与删除规则，并实际做恢复演练。

七、生命周期、应用重启与故障恢复

操作控制行为数据与任务语义
首次创建 / Start首次分配 desktop_id 与用户卷；后续 Start 复用它们。记录期望状态后异步启动，返回操作 ID，不阻塞对话等待桌面就绪。只有通过卷挂载、Compute Agent 和桌面 Ready 检查后才报告可用；重复请求不创建第二个用户盘或 VM。
Status / 重连结合持久记录与运行时实际状态返回 starting、running、stopping、stopped、error 或待核实状态。连接断开不等于 VM 已关机；Manager 重建后先对账，而不是盲目重新创建电脑。
Stop / 普通关机确认作用于整台用户电脑，通知相关任务收尾；Guest 优雅关机、刷盘，再由运行时确认进程停止。超时进入明确异常处理。保留磁盘与电脑身份。会影响该用户所有 Bot 的活动桌面和 Guest 内 Job，不能与停止一个 Job 混为一谈。
Pause / 快照休眠不是首版必需功能。Pause 仍保留 VM 运行资源；快照休眠需要额外的一致性、兼容性与存储管理。不能把单纯暂停当成释放全部 Guest 内存；是否启用和如何恢复，单独验证。
Delete / 重置独立的高风险管理操作，明确确认、审计、备份及回收策略；不由 Pod 清理钩子自动触发。删除盘、清空用户数据或恢复到模板都具有破坏性，必须与开关机区分。

Compute Agent 管理 Guest 内桌面与 Job；Compute Manager 管理整台云电脑。生命周期操作与状态通过现有异步事件体系回报 Router，不新增一套面向用户的主对话入口。

应用控制 / 会话重连 基础设施查询与绑定 发生重启的应用 Pod 虚线表示返回或生命周期参考线

应用整体重新部署，只要计算节点与独立存储未被连带销毁，云电脑可继续运行；如果连宿主也关机，内存和进程不能因此获得永久性，需要走下表的恢复路径。

故障范围应该保留什么恢复方式与边界
业务 Pod / Manager 重启VM、Guest 进程、用户盘与持久归属记录均不随之销毁。新 Manager 对账后重新绑定；不能将“连接丢失”解释为需要重新创建用户环境。
Desktop Gateway 重启VM 与磁盘继续存在；现有 VNC / 控制连接可能断开。恢复路由和授权后重连同一 screen_id；传输会话可以重建，用户盘不能随会话清理。
Compute Agent / Guest 重启用户盘保留；Guest 重启会丢失普通 RAM、进程与未保存界面状态。服务重新就绪并重建屏幕映射；Job 状态先核对，不把进程消失写成成功，也不盲目重放有副作用操作。
计算节点或整个计算层重启依靠外部持久块存储与控制目录保留已可靠落盘的数据，不承诺原 RAM 仍在。确认旧实例失效并解除旧挂载，在可用节点挂载原卷后冷启动；存储本身故障则按备份及约定 RPO / RTO 恢复。
“数据不能丢”要落实到故障域，而不是一句绝对承诺。业务 Pod 重启不得造成用户数据丢失是硬约束；宿主断电、存储故障下的最新未刷盘数据、备份恢复点与恢复时间，需要用存储方案和故障演练验证。本文不虚构零 RPO 或零中断 SLA。

八、安全与访问边界

  • 宿主隔离：使用受支持的 Linux / KVM 环境、生产约束下的 jailer / seccomp / cgroup / 命名空间与非特权身份；宿主、Guest 内核与微码持续更新。[8]
  • 管理接口隔离：Firecracker 控制 Socket、宿主文件与挂载权限仅供节点运行时使用；业务 Pod 不直接获得宿主设备权限，Guest 和浏览器也不能调用宿主开关机接口。
  • 屏幕授权：Desktop Gateway 验证用户、desktop_id、Bot / screen_id、运行代次与只读 / 控制范围，使用短时会话凭证；不能凭一个 screen_id 就访问画面或注入键鼠。
  • 网络隔离：按用户划分网络与出站策略，限制访问其他用户 VM、宿主管理网和云元数据服务；VNC / Agent 通道经受控私网或隧道访问，不裸露公网端口。
  • 敏感数据：共享 Profile、Cookie、下载与磁盘备份本身就可能承载敏感权限。沿用 Vault / Security Form 受控注入，不把秘密写入模型上下文、普通事件载荷或审计日志。
  • 共享 Guest 的信任前提：应用层的 Bot 权限管理不能单独阻止同一 Guest 内任意代码读取共享登录态。若需要真正相互不信任的工作负载，应使用独立用户 / 计算安全域，不假装屏幕裁剪已经解决。

具体网络实现、身份凭证格式、存储加密 / 密钥管理与审计保留期另行设计；这些边界不能因采用 microVM 就被省略。

九、容量、并发与运营约束

围绕 2 vCPU / 4GB 约束并发

  • 屏幕按需创建，限制活跃 Chrome 标签、图形输入、后台 Job、Python 进程和磁盘写入，不因一个用户有十个 Bot 就默认启动十套满载桌面。
  • GUI 控制权与长任务分离：等待桌面操作时，Router 仍可接收消息；非 GUI Job 可在预算内并行，不能用一个长回合把整台云电脑锁住。
  • 持续监测 Guest RSS / OOM、CPU、磁盘余量与 I/O、Agent 心跳、VNC 帧率与延迟；日志、缓存和安装包需要配额及清理。
  • 冷启动、浏览器启动和桌面 Ready 分别计量，不使用 Hypervisor 的宣传启动数字替代真实用户体验。

容量计算不能只看 Guest 配额

以 1,000 位用户全部开机、Guest 内存按建议的 4 GiB 配置估算：

  • CPU：2,000 个虚拟 CPU 配额，不等于可以无损超卖，也不等于已经预留 2,000 个物理核心。
  • 内存：4,000 GiB Guest 内存，另加宿主内核、Firecracker、网关、存储缓存和安全余量。
  • 磁盘：40 TB 十进制逻辑用户卷容量，另算基础镜像、副本、备份和可选内存快照；薄置备不是容量保障。
  • 成本：关机可释放运行资源，但用户卷与备份仍占空间并可能计费；是否休眠、何时回收运行资源需另定策略。

这些是规格推算，不是压测结果、节点装箱承诺或云厂商报价。用户配额、超卖比例与实际并发上限必须压测后确定。

十、落地验证与资料依据

上线前必须留下的验证证据

  1. 单 VM 桌面可用：在 2 vCPU / 4GB / 40GB 下验证中文网页、PDF、文件浏览器、终端、Python 与 VNC 观察 / 接管；记录 Ready、帧率和资源占用。
  2. 多屏与共享浏览器：验证多个 Bot 视图、共享 Cookie、窗口归属、弹窗、文件选择器、全局焦点和人工接管；检查错误屏幕输入与越界画面，不把 Profile 锁问题藏成偶发故障。
  3. 应用重启不丢电脑：写入并可靠落盘测试文件，记录 desktop_id / volume_id；重启业务 Pod 与 Gateway，确认连接恢复后原文件、Profile 和原 VM 归属仍在。
  4. Guest / 宿主故障恢复：分别重启 Guest、终止运行时、模拟节点失联；验证同一卷单写入者、旧代次隔离、文件完整性与 Job 实际状态核对。
  5. 备份与权限：实际从备份恢复；测试跨用户访问、过期屏幕凭证、无控制权输入、未授权开关机和凭据泄漏防护。

当前只完成架构与公开资料核对；上述验证尚未执行。多屏窗口方案、持久块存储后端、Firecracker / 内核版本、重启恢复指标和容量上限，是后续实现的明确验收项。
