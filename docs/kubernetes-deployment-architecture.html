K3s / Kubernetes：Pod 分布与业务分层

一、部署结论与设计范围

四类独立 Deployment，每类独立发布、独立扩容、多 Pod 副本。Go 负责业务接入、确定性运行调度与桌面代理；TypeScript 单独承担 Agent Runtime。不是把四个模块或四个容器塞进一个 App Pod，也不是给每个用户、Bot 或 Agent 都创建一个 Pod。

当前以 K3s 部署，采用 Kubernetes（K8s）的 Deployment、Service、健康检查与资源调度机制表达工作负载，保留迁移到其他 Kubernetes 发行版的空间。发行版相关的 Ingress、存储与节点配置单独管理，不把 K3s 的默认行为当作跨集群保证。

业务拆成 api-gateway、scheduler、agent-runtime、desktop-gateway 四组。每组拥有独立进程入口、镜像发布与副本配置；Go 服务可以复用同一代码仓库和领域基础包，但不能靠进程内调用绕过已定义的服务边界。

两个“调度器”不要混淆。本项目的 Go Scheduler 调度业务事件、Session、Job 与用户云电脑；Kubernetes 的 kube-scheduler 调度 Pod 到节点。前者不是替换后者，也不意味着每个业务 Job 必须创建一个 Kubernetes Job。

本专题补充 技术架构 与 云电脑架构 的物理部署边界。云电脑文档中曾放在 App Pod 内的 Compute Manager，在本部署约定中归入独立 Go Scheduler；不再另设一个包揽所有业务的 App Pod。本文不修改旧文档，也不表示已生成部署清单或完成上线。

二、四类 Deployment 与多副本 Pod 分布

业务接入 / 智能执行 业务调度 / 连接代理 部署与基础设施生命周期边界

副本数仅用于说明部署关系，不是容量或高可用承诺。底部表示独立生命周期，不强制数据库位于集群外，也不要求计算宿主不能加入 K3s；关键是 VM 与数据不能依附业务 Pod 存活。

以下为建议的 Deployment / 服务命名，尚未创建 Kubernetes 资源。
独立服务语言与主要职责独立伸缩依据
api-gatewayGo：组织 / 用户 / Bot 配置、鉴权、聊天 API、渠道回调、WebSocket 与事件规范化。请求延迟、请求量、活跃连接数；不与模型调用并发数绑定。
schedulerGo：Router Dispatch、订阅投递、Session 所有权、配额、超时与恢复、执行控制、Compute Manager。待分派事件、调度延迟、租约冲突、恢复积压；不能让多个副本同时抢写同一对象。
agent-runtimeTS：Router Pool、Main / Work / Worker Session、模型调用、工具选择和语义编排。活跃模型请求、会话内存、待处理输入与模型供应商限额；不能只按 CPU 决定扩缩。
desktop-gatewayGo：屏幕连接、VNC / Agent 隧道、会话鉴权、控制与人工接管代理。并发桌面连接、带宽、转发延迟与连接缓冲；不因业务 API 发布而一起重启。
Deployment、Pod、逻辑 Agent 是三个层次。一个 Deployment 管理多个同类 Pod；一个 Agent Runtime Pod 承载多个逻辑 Agent / Session；一个用户仍只有一个逻辑 Router，但它可以在不同 Runtime Pod 之间受控迁移。[1]

三、业务分层与 TS / Go 职责

TypeScript：决定做什么

  • Router 理解人的意图，决定是否回复、创建哪些 Ticket，并统一组织对外沟通。
  • Ticket 和 Worker 管理任务目标、工作上下文、下一步模型推理与工具选择。
  • 提出订阅、Job 操作和云电脑能力请求；收到事件后继续判断，不亲自管理宿主进程或持久卷。
  • Router、Ticket、Worker 首版共用 Agent Runtime 部署，内部保持模块与 Session 隔离；它们不是三个额外 Deployment。

Go：管理执行如何发生

  • API 处理业务配置、接入身份、事件来源与渠道输出；基础设施权限不交给模型进程。
  • Scheduler 按授权、订阅和 Session 所有者进行确定性分派，管理执行配额、租约、超时和恢复。
  • Compute Manager 作为 Scheduler 内部模块提交用户 VM 生命周期操作，不再藏在一个总控 App Pod 里。
  • Desktop Gateway 专职连接与代理，不成为第二个模型 Router，也不承担业务任务规划。
领域状态 / 能力主要负责服务边界
用户、Bot、渠道、消息与 Thread 元数据API Gateway / Go保留可信用户身份、来源会话与 Bot 归属；授权不能只在入口检查一次。
推理上下文、任务目标与 Session 检查点Agent Runtime / TS语义编排态由 Agent 维护；不擅自覆盖 Go 管理的执行终态。
订阅路由、Session 租约与运行分配Scheduler / GoAgent 通过明确请求表达订阅意图；调度控制面负责有效路由与所有权协调。
Job 执行状态、重试与取消记录Scheduler / Go根据 Node Runtime / Compute Agent 的实际结果推进；发出 Start 或 Stop 不等于已经完成。
云电脑归属、期望状态、运行代次与卷绑定Scheduler 内的 Compute Manager / Go真正开关机与挂载由宿主运行时执行；不能由业务 Pod 进程树持有 VM 生命周期。
桌面连接与控制权校验Desktop Gateway + Guest Compute Agent连接临时存在于网关；目标映射与权限可恢复，控制权不能只靠某个网关 Pod 的内存锁。

可以共用一个 PostgreSQL 集群，但要划分领域表 / schema、写入身份与命令边界。任务目标、Agent 编排态和 Job 运行态是不同对象；同一个状态字段只设一个权威写入方，不在 TS、Go 两侧各造一套相互同步的状态机。

四、消息接入、执行与结果回传

业务输入 / Agent 请求 / 用户输出 确定性调度 / 执行与状态回传 虚线表示确认、事件或结果回传；竖虚线为生命线

图中 Event Bus 是逻辑传递层，持久事件与流式输出采用不同传递语义。第⑥步省略 Desktop Gateway 的受控代理 / Agent 隧道；实际执行仍由 Node Runtime 与 Guest Compute Agent 完成。不是所有工具都必须进入 VM，本文只展开已有云电脑执行路径。

  • 首次事件：交对应用户的 Router 理解意图；需要长任务时创建 Ticket 和 Worker，不把整个工作放在 API 请求或一个阻塞式 ReAct 回合中。
  • 已有订阅：Router Dispatch 根据 Thread 与 Ticket 的多对多订阅，直接投递到目标 Ticket / Worker 的会话所有者，不强制再调用 Router 模型。
  • 人的新消息：仍由用户 Router 统筹；命中订阅时相关任务可同时消费。Job 完成、控制、输入和输出可以异步发生，不等后台工作结束才接收消息。
  • 通信契约：同步查询先用 HTTP / JSON，异步协作用版本化事件 / 命令；携带 event_id、可信用户与 Bot 标识、目标 Session / Job、关联 ID 和必要代次。Start / Stop 等副作用请求还需要稳定的 operation_id。

模型增量输出不能作为新的用户输入再次触发 Agent；桌面画面不经过模型调度。所有入口与执行边界保留 Policy、Vault / Security Form 和敏感数据约束，不因服务位于内网而取消授权检查。

五、可替换 Pod 与有状态 Session

逻辑会话有状态，但 Pod 不保存唯一的持久状态。Agent Runtime 内可以有上下文缓存、活动模型连接与临时输入队列；这些不是唯一事实来源。持久检查点、输入接收记录、执行关联与租约放在外部存储，Pod 消失后可由其他副本恢复。

可替换的 Runtime 副本 持久所有权 / 有效状态与命令准入 故障与旧代次请求拒绝路径

图中 epoch 7 / 8 是说明机制的示例，不是已实现协议。Session 所有权与 VM / 用户卷单写入者代次属于不同作用域，不能混成一个全局版本号；租约时长与失效检测阈值尚未确定。

  • 定向投递，不靠随机负载均衡：Kubernetes Service 提供稳定入口和后端发现，但不天然理解 user_id 或 Session 所有权。业务事件由 Scheduler 定向到 owner；只做粘性会话不能代替持久租约与故障接管。[2]
  • 所有者粒度是会话：每用户一个逻辑 Router，同用户多个 Bot 共用它；Ticket / Worker 保持各自独立 Session。不同会话可落在不同 Runtime Pod，不用一把覆盖全用户长任务的锁。
  • 先可靠接收，再确认消息：输入写入可恢复的会话状态或收件记录后才能确认消费；不能只丢进内存队列就 ACK，也不应把整个模型 / Job 生命周期绑在一次队列消费回调里。
  • 恢复不是从头重跑：先读取检查点、去重记录与已有 operation_id / job_id，查询外部执行实际状态。进行中的模型连接可能中断，需要明确恢复或失败重试，不声称 TCP / 模型生成可以自动迁移。
  • 不承诺外部副作用天然恰好一次：状态幂等、代次校验和操作记录要落到执行入口；已经发生的网页提交、发信或文件修改，不能仅因 Pod 换了就安全重放。

六、消息系统、持久数据与基础设施

基础设施首版建议用途部署与持久化约束
PostgreSQL业务事实、Session 检查点、租约、任务 / Job 状态、订阅与用户 VM 归属；按领域明确表的写入责任。托管数据库或专门的有状态工作负载。不能把数据库 Pod 复制三份就视为已具备复制与故障切换。
NATS JetStream作为单一消息系统的起步建议，承载需要可靠投递的输入、控制、执行与完成事件；TS / Go 使用版本化契约通信。配置持久化、确认、重投、保留上限与消费位置。消息可能重复，消费者必须幂等；具体版本与 HA 拓扑另行锁定。
流式输出 / 桌面传输模型增量输出经独立流式通道，VNC 画面经 Desktop Gateway；最终消息与任务结果保留持久记录。不把每个 token 或 VNC 帧写进持久任务队列；连接断开后的重连、结果补查与权限校验由对应入口处理。
对象存储与用户块卷Artifact、备份与用户电脑持久磁盘；保留 user_id、desktop_id、volume_id 的可信关联。独立于业务 Pod；用户块卷需要单写入者与跨节点恢复能力。对象存储不能直接当作 Firecracker 的可写块盘使用。
消息投递与任务事实要可靠衔接。状态变更与待发布事件可使用事务 Outbox；消费侧在可靠记录输入或结果后确认，并以 event_id / operation_id 去重。Outbox 是服务内部持久化与发布机制，不需要因此增加第五类业务 Deployment。

负载均衡与事件扇出不同

同一个消费者由多个副本分工处理，用于负载均衡；多个独立订阅者都需要看到同一事件，则需要独立消费位置或明确的应用层扇出。Thread 的多 Ticket 订阅不能通过把它们塞入同一个竞争消费组来实现。

JetStream 的确认、重投与保留策略需要一并设计；不能把“至少一次”解释为“无重复”或“永不丢弃直到处理”。[3]

控制流与噪声流不同

停止、授权、失败和完成事件不能被大量进度消息长期阻塞。常规进度可以合并或限频；控制事件需要独立的处理预算与通道约束，且不等待某个模型回合或 Job 先结束。

本轮确定消息语义与隔离原则，不冻结 topic 名、分片数、消费者数量或优先级阈值；先不同时引入多套队列。

七、节点分布、发布与故障边界

K3s / Kubernetes 节点职责

  • 集群控制平面：由 K3s / Kubernetes 管理 API Server、集群状态和 Pod 调度；不计入四类业务 Deployment。
  • 通用业务节点：运行 API、Scheduler、Agent Runtime 与 Desktop Gateway 的 Pod；以资源请求 / 限制、调度约束与拓扑分散控制资源及故障域，不要求每类独占物理节点。
  • 计算节点：具备 Linux / KVM，优先由宿主 systemd 托管 Node Runtime；Firecracker VM 使用独立服务 / 运行作用域，不能因业务 Pod 或管理进程的重启被默认连带终止。
  • Guest 内：每用户 microVM 保留 Compute Agent、浏览器、屏幕与 Job；Compute Agent 不是第五类 Kubernetes 业务 Pod，实际执行也不是默认创建 Kubernetes Job。
K3s 默认 local-path 不是跨节点持久化保证。它使用节点本地存储，不能直接满足“原计算节点故障后，在另一节点恢复同一用户盘”的要求。数据库、消息持久化与用户卷分别选择匹配故障域的存储、保留和备份策略。[4]
发布 / 故障对象应该如何退出与恢复不应影响什么
API Gateway Pod摘除新流量，处理连接排空；客户端重连到其他副本，已持久接收的消息不重复创建任务。不重启 Agent Runtime，不停止用户 VM / Job，不清空 Thread 或会话记录。
Agent Runtime Pod停止认领新会话，保存检查点并受控交接 / 释放租约；必要时中断模型生成，新 owner 核对已有 Job 后续行。不因本 Pod 退出而自动停止全部 Guest Job，更不终止 Firecracker 或删除用户盘。
Scheduler Pod释放 / 接管调度所有权，恢复未完成操作；多副本根据租约、操作幂等与实际状态协调。不重复 Start 同一 Job / VM；不能把控制连接断开等同于执行失败或电脑已经关机。
Desktop Gateway Pod排空或重建桌面连接，按有效授权重新绑定同一 VM / screen_id；人工控制权由统一边界校验。不删除屏幕规格，不重建浏览器 Profile，不销毁 VM。
数据库 / 消息系统 / 计算节点使用各自的持久化与恢复方案；基础设施不可用时停止未经确认的接管和副作用命令，故障后对账。不能仅因业务 Pod 有多个副本就宣称整个平台已经高可用或数据零丢失。

使用 startup / readiness / liveness 检查、合理退出宽限期与滚动更新策略。readiness 不是长连接迁移机制；PDB 主要约束符合条件的自愿驱逐，不能阻止所有节点故障、直接删除或发布中断。[1][5]

网络、权限与独立发布

  • 复用集群已有 Ingress / 入口能力，按需暴露 API 和桌面网关；Scheduler、Agent Runtime、数据库与宿主控制接口不直接暴露公网。
  • 每类服务使用独立身份、最小权限与网络访问范围；Node Runtime 的宿主权限不扩散给 TS 模型进程或普通 API Pod。
  • 多副本分散到适当故障域；单节点上的多个 Pod 可以抵抗进程失败，但不能抵抗该节点整体失效。
  • 消息和 HTTP 契约需要版本兼容，数据库迁移先兼容新旧副本；共享代码仓库不要求四个服务永远一起发布。

场景业务 Pod 数量解释

本机部署数据库与消息系统的开发示例4 个业务 + 2 个基础设施 = 6假设 PostgreSQL 与 NATS 各一个开发实例；不含集群系统、前端、对象存储、用户 VM 等，不作为生产 HA 配置。

先固定四个物理部署边界，不按每个概念拆一个微服务。Policy、Memory、Thread、Artifact 等先作为归属明确的领域模块；Router / Ticket / Worker 首版共用 Agent Runtime。只有出现独立伸缩、权限或发布边界的实际需求，再继续拆分。

实现时需要验证的最小闭环

  1. 真实分布：四个 Deployment 各自有独立 Pod、入口与发布配置；扩容 Agent Runtime 不要求同步扩容或重启 API。
  2. 异步闭环：输入经过 API 与 Scheduler 进入 TS Runtime，Worker 提交 Job 后释放长等待；新的用户输入和 Stop 控制仍可及时处理。
  3. 所有权与恢复：两个 Runtime 同时竞争一个 Session 时只有一个有效 owner；旧 owner 的迟到写入、输出与执行请求被拒绝。
  4. 订阅与幂等：一个 Thread 的多个订阅 Ticket 都能收到获准事件；重复投递与发布重试不会重复启动同一执行。
  5. 发布不伤及云电脑：分别重启四类业务 Pod，核对 desktop_id、volume_id 和运行中的 VM；Runtime 恢复先核对原 Job，不盲目重放副作用。
  6. 故障域：模拟节点与存储故障，验证持久数据、租约接管和连接恢复，区分业务多副本、集群 HA 与数据耐久性。

参考与边界依据

  1. Kubernetes Deployments：副本管理与滚动发布；Container probes：启动、就绪与存活检查。
  2. Kubernetes Services：服务入口与后端 Pod 发现；业务 Session 所有权需由应用另行设计。
  3. NATS JetStream；Pull consumers；Retention policies：持久消息、重投、消费者分工与保留语义。
  4. K3s Volumes and Storage：默认本地存储及其节点关联；Kubernetes Persistent Volumes：持久卷生命周期与回收策略。
  5. Kubernetes Disruptions：PDB 与自愿 / 非自愿中断的适用边界。
